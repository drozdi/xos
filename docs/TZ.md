Техническое задание на разработку системы XOS
(Серверная и клиентская части)

1. Общие сведения

Наименование проекта: XOS (рабочее название) – веб-ориентированная CRM-система с десктоп-окружением в стиле Windows.

Назначение:

```
Серверная часть – предоставляет REST API для управления устройствами, пользователями, ролями, правами доступа, информационными блоками и настройками.

Клиентская часть – реализует полноценное десктоп-окружение в браузере, позволяющее запускать бизнес-приложения в отдельных окнах с возможностью перемещения, изменения размера, группировки и сохранения состояния.
```

Команда разработки: внутренняя команда.
2. Общая архитектура

Система построена по клиент-серверному принципу:

```
Сервер: PHP 8.2+, Symfony 7.3, Doctrine ORM/DBAL, MySQL.

Клиент: React + TypeScript, Vite, Tailwind CSS, Mantine, Zustand, TanStack Query, Axios, Zod, react-rnd, react-window.
```

Взаимодействие осуществляется через REST API с использованием JWT-аутентификации. Клиентское приложение – одностраничное (SPA), без маршрутизации – переход между экранами входа и рабочим столом осуществляется по флагу аутентификации.
3. Стек технологий
3.1. Серверная часть

```
Язык: PHP 8.2+

Фреймворк: Symfony 7.3 (компоненты: framework-bundle, security-bundle, console, dotenv, validator, yaml, translation, mime, debug-bundle, runtime)

ORM/DBAL: Doctrine ORM 3.4, Doctrine DBAL 3, Doctrine Bundle 2.14, Doctrine Migrations Bundle 3.4

Аутентификация/авторизация: Lexik JWT Authentication Bundle 3.1, Gesdinet JWT Refresh Token Bundle 1.5

CORS: Nelmio CORS Bundle 2.5

База данных: MySQL (через Doctrine DBAL)

Инструменты разработки: Symfony Maker Bundle, Symfony Web Profiler Bundle
```

3.2. Клиентская часть

```
Библиотека UI: React 18+ с TypeScript

Сборка: Vite

Стили: Tailwind CSS + кастомные медиа-запросы для окон

UI-компоненты: Mantine (кнопки, инпуты, селекты, модалки, таблицы, уведомления, формы)

Управление состоянием: Zustand (глобальные сторы)

```

1. Функциональные требования

4.1. Серверная часть (Backend)
4.1.1. Модули и сущности

Сервер организован по модульному принципу. Основные модули:

Модуль App (ядро)

```
Контроллеры:

    ApiLoginController – аутентификация (вход, выход, проверка сессии, получение данных пользователя, обновление JWT).

    ApiAccountController – управление учётной записью (получение детальной информации, карты доступа, уровней доступа, ролей, опций; обновление профиля и опций).

    ApiScopeController – дублирует часть функционала для работы с областями доступа.

Сущность: RefreshToken – токен обновления JWT.
```

Модуль Device

```
Сущности: Device, License, Software, Accounting, Property, PropertyEnum, Type.

Реализует CRUD и бизнес-логику для устройств, лицензий, ПО, свойств.
```

Модуль IBlock (информационные блоки)

```
Сущности: Block, Element, Property, Section, Type.

Предназначен для гибкого управления структурированными данными (аналогично инфоблокам).
```

Модуль Main (основные справочники)

```
Сущности: User, Group, Role, OU (организационная единица), Claimant, File, StoredAuth.

Управление пользователями, ролями, группами, организационной структурой, файлами.
```

Метод	URL	Описание	Авторизация

GET	/login-check	Проверка статуса аутентификации	Да

POST	/refresh-token	Обновление access-токена по refresh-токену	Да
GET	/account	Детальная информация о пользователе	Да
GET	/account/map	Карта доступа (разрешения)	Да
GET	/account/accesses	Уровни доступа пользователя	Да
GET	/account/roles	Роли пользователя	Да
GET	/account/options	Опции пользователя (настройки)	Да
PUT	/account/options	Обновление опций (сохранение настроек)	Да
PUT	/account	Обновление профиля (email, alias, ФИО, описание, пароль)	Да
CRUD для устройств, инфоблоков, пользователей	…	Полный набор эндпоинтов для управления соответствующими сущностями (GET, POST, PUT, DELETE)	Да (с проверкой ролей/скоупов)

Дополнительные эндпоинты для системы настроек (если используется ApiAdapter):

```
GET /api/settings/:key – получить значение настройки.

POST /api/settings – сохранить настройку (или пакет настроек).

DELETE /api/settings/:key – удалить настройку.

GET /api/settings – получить все настройки пользователя (для предзагрузки).
```

Примечание: сервер должен поддерживать хранение пользовательских настроек в базе данных (например, в коллекции user_settings), привязанных к пользователю.
4.1.3. Аутентификация и безопасность

```
JWT-токены (access + refresh) с настраиваемым временем жизни.

Хеширование паролей через Symfony Password Hasher.

Ролевая модель с возможностью иерархии (через символ _).

Скоупы (битовые маски) для тонкой настройки прав на действия.

CORS настроен через NelmioCorsBundle (разрешённые origins задаются конфигурацией).
```

4.1.4. База данных

```
MySQL.

Миграции управляются через Doctrine Migrations.

Основные коллекции: пользователи, устройства, лицензии, информационные блоки, настройки и др.
```

4.2. Клиентская часть (Frontend)
4.2.1. Window Manager (Менеджер окон)

```
Управление жизненным циклом окон: открытие, закрытие (с возможностью отмены через onClose), сворачивание, разворачивание на весь экран, восстановление исходного размера, перезагрузка содержимого, активация (фокус).

Параметры окна: wmGroup (группировка в панели задач), wmSort (порядок внутри группы), размеры, позиция.

Все изменения позиции, размера и состояния автоматически сохраняются в системе настроек (категория WIN, ключ привязан к appId).

При загрузке страницы окна восстанавливаются из сохранённых настроек.

Дочерние окна (диалоги, модалки) создаются через windowApi.createChildWindow и не регистрируются в глобальном Window Manager и не отображаются в панели задач.

Адаптивность окон: на экранах <768px окна занимают 100% ширины и высоты (за вычетом панели задач), кнопки управления увеличены.
```

4.2.2. App Manager (Менеджер приложений)

```
Регистрация приложений через манифест (AppManifest): id, name, version, icon, component, размеры по умолчанию, минимальные размеры, requiredRole, requiredScope, wmGroup, singleInstance (флаг единственного экземпляра), instanceKey (ключ для уникальности экземпляра).

Запуск приложения (launchApp) с проверкой singleInstance:

    Если приложение уже открыто (по id + instanceKey) – существующее окно фокусируется и восстанавливается, новое не создаётся.

    Иначе создаётся новое окно.

Динамическая загрузка приложений через import.meta.glob (code splitting).

История запусков сохраняется в localStorage; при перезагрузке страницы все ранее открытые приложения восстанавливаются (с учётом singleInstance).
```

4.2.3. Taskbar (Панель задач)

```
Меню «Пуск»: выпадающий список всех доступных пользователю приложений (фильтрация по ролям/скоупам). Клик по пункту запускает приложение.

Список запущенных окон с группировкой по wmGroup:

    Окна с одинаковым wmGroup объединяются в одну кнопку.

    При наведении/клике на кнопку группы отображается выпадающее меню со списком окон группы (отсортированных по wmSort), позволяющее активировать или закрыть конкретное окно.

    Клик по кнопке группы (не по меню) сворачивает все окна группы, если какое-то активно; если все свёрнуты – восстанавливает последнее активное.
```

4.2.4. Система макетов (Layout)

```
Макет задаётся строкой view (например, "hhh lmr ffr"), которая парсится в сетку на CSS Grid.

Боковые панели (l и r) поддерживают изменение ширины перетаскиванием разделителя, ширина сохраняется в настройках.

При ширине панели менее порога (например, 50px) она сворачивается в адаптивный режим (overlay с кнопкой-гамбургером).

Для мобильных устройств (<768px) используется отдельная строка mobileView.
```



4.2.5. Система прав доступа (Roles & Scopes)

```
Клиент получает роли и скоупы с сервера при аутентификации.

Роли: массив строк с возможной иерархией (через _). Методы: isRole, isRoot, isAdmin.

Скоупы: объект с ключами (название параметра) и числовыми уровнями (битовые маски). Методы: checkHasScope, getLevelScope, getCanScope.

Используются для фильтрации доступных приложений и внутри приложений для контроля UI-элементов.
```

4.2.6. Система настроек (SettingManager + адаптеры)

```
Приоритеты: USER (пользовательские) > APP (приложений) > WIN (окон) > HKEY_CONFIG (умолчания).

Категории: USER, APP, WIN, HKEY_CONFIG.

Методы: get, set, has, remove, sub.

Адаптеры хранения (реализуют интерфейс ISettingAdapter):

    LocalStorageAdapter – синхронное хранение в localStorage (используется по умолчанию).

    ApiAdapter – асинхронное хранение через REST API (запросы к серверу).

    CompositeAdapter – комбинация адаптеров (например, чтение из кэша, запись в оба).

При инициализации выбирается адаптер в зависимости от конфигурации (флаг USE_API_SETTINGS).

Реактивные хуки: useSetting, useSetState для чтения/записи настроек с автоматическим сохранением.
```

4.2.7. Core API для приложений

Каждое приложение при монтировании получает объект coreApi через контекст:
typescript

```
interface CoreApi {
  // HTTP-клиент с уже настроенными интерцепторами (авторизация, обработка ошибок)
  http: AxiosInstance;
  
  // Уведомления (Mantine Notifications)
  toast: {
	show: (payload: NotificationPayload) => void;
	success: (message: string) => void;
	error: (message: string) => void;
	info: (message: string) => void;
	warning: (message: string) => void;
  };
  
  // Аутентификация
  auth: {
	getUser: () => User | null;
	logout: () => void;
  };
  
  // Управление своим окном (главным окном приложения)
  window: WindowApi;
  
  // Права доступа
  roles: {
	isRole: (role: string) => boolean;
	isRoot: () => boolean;
	isAdmin: (mod?: string) => boolean;
  };
  scopes: {
	checkHasScope: (scope: string) => boolean;
	getLevelScope: (scope: string) => number;
	getCanScope: (scope: string) => number;
  };
  
  // Менеджер настроек (полный доступ)
  settings: SettingManager;
}

http – настроенный экземпляр Axios (с интерцепторами для авторизации и обработки ошибок).

toast – уведомления (Mantine Notifications).

auth – методы getUser, logout.

window – WindowApi для управления собственным окном (и созданием дочерних).

roles и scopes – проверка прав.

settings – доступ к SettingManager.
```

WindowApi предоставляет: close, minimize, maximize, restore, refresh, setTitle, setSize, setPosition, on/off для событий, createChildWindow.
4.2.8. Адаптивная вёрстка внутри окон

```
Хук useWindowSize возвращает текущие размеры окна приложения.

Кастомные Tailwind-брейкпоинты с префиксом window: (например, window:max-window-sm:flex-col).
```

1. Требования к интеграции сервера и клиента

5.1. Аутентификация

```
При входе клиент отправляет запрос POST /login с логином/паролем, получает access и refresh токены.

Access-токен передаётся в заголовке Authorization: Bearer <token> при каждом запросе.

При истечении access-токена клиент использует POST /refresh-token для получения новой пары.

При выходе (/logout) refresh-токен удаляется на сервере.
```

5.2. Передача прав

```
При успешной аутентификации сервер возвращает данные пользователя, включая массив ролей и объект скоупов.

Клиент сохраняет их в сторе и использует для фильтрации UI и проверок.
```

5.3. Работа с настройками

```
Если клиент использует ApiAdapter, то при вызове settingManager.set(key, value) отправляется POST /api/settings с телом { key, value }.

При старте клиент может загрузить все настройки пользователя через GET /api/settings для предварительного заполнения кэша.

Сервер должен обеспечить хранение настроек в базе данных, привязанных к пользователю (например, коллекция user_settings).
```

5.4. Обработка ошибок

```
Клиентские интерцепторы Axios обрабатывают 401 (попытка обновить токен), 403 (доступ запрещён), 500 и другие ошибки с выводом понятных уведомлений.

На сервере должны быть реализованы валидация входных данных и соответствующие HTTP-статусы.
```

1. Нефункциональные требования

6.1. Производительность

```
Время загрузки первого экрана (клиент) < 2 с при скорости 1 Мбит/с.

Размер основного бандла клиента < 200 КБ (gzip).

Перетаскивание и изменение размера окон – 60 FPS.

Для списков >100 элементов – виртуализация (react-window).

Минимизация запросов к серверу за счёт кэширования (TanStack Query, кэш настроек).
```

6.2. Масштабируемость

```
Добавление новых приложений на клиенте не требует изменений в ядре – достаточно создать модуль в src/apps/.

На сервере модульная структура позволяет легко расширять функциональность новыми сущностями и контроллерами.
```

6.3. Отказоустойчивость

```
Каждое окно клиента изолировано Error Boundary – ошибка в одном не влияет на другие.

Состояние окон и настроек сохраняется (localStorage или сервер), позволяя восстановить интерфейс после перезагрузки.

Интерцепторы Axios обрабатывают сетевые ошибки; при недоступности API-адаптера – fallback на локальное хранилище.
```

6.4. Безопасность

```
Хранение токенов рекомендуется в httpOnly cookies (по возможности); при использовании localStorage – короткоживущие токены и регулярное обновление.

Все проверки прав дублируются на сервере – клиентские проверки только для UI.

Защита от XSS (React экранирует данные).
```

6.5. Кроссбраузерность

```
Поддержка последних версий Chrome, Firefox, Safari, Edge.
```

6.6. Доступность (a11y)

```
Корректные ARIA-атрибуты (Mantine предоставляет по умолчанию).

Клавиатурная навигация (Tab, Enter, Escape) для всех интерактивных элементов.
```

9. Критерии приемки
9.1. Функциональные

```
Сервер успешно аутентифицирует пользователей и возвращает корректные данные.

Все заявленные API-эндпоинты работают и возвращают ожидаемые структуры.

Клиентское приложение загружается, отображает рабочий стол с окнами.

Окна открываются, закрываются, сворачиваются, разворачиваются, перемещаются и изменяют размер.

Группировка окон в панели задач работает согласно спецификации.

Приложения с singleInstance: true открываются в единственном экземпляре.

Настройки сохраняются и восстанавливаются (как локально, так и на сервере при использовании ApiAdapter).

Права доступа корректно фильтруют список доступных приложений и элементы внутри них.

Макет адаптируется под размер экрана и сохраняет ширину боковых панелей.
```



9.2. Нефункциональные

```
Время загрузки < 2 с, размер бандла < 200 КБ.

Перетаскивание окон плавное (60 FPS).

Ошибка в одном окне не приводит к падению всего приложения.

Код покрыт тестами не менее 70% для критических модулей.

Документация содержит примеры создания новых приложений и адаптеров настроек.
```
