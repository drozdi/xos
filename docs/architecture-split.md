# Разделение XOS и агента Samba

Дата обзора: 2026-11-13. База: `7070dbf` на `master`. Это проект, код разделения не пишется.

По репозиторию нет прикладного Samba: поиск `samba`, `smb.conf`, `samba-tool`, `winbind`, `krb5`, `netbios` в PHP, TypeScript, YAML и Markdown ничего не даёт. Управлять файловым сервером и контроллером домена сейчас нечем. Ниже — что реально собрано, какой из существующих механизмов годится как образец, и как разрезать систему на центральное приложение и агент на каждом хосте Samba.

## 1. Текущий проект

### 1.1 Назначение

XOS — рабочий стол в браузере. Пользователь входит, видит стол, «Пуск» и окна приложений. Данные приложений лежат в MySQL и доступны после входа с другого устройства. Оболочка не знает предметных правил модулей. Модуль не рисует стол и не хранит геометрию окон (`docs/TZ.md`).

Идея владельца — централизованно управлять Samba, где хост может быть файловым сервером, контроллером домена AD или совмещать оба — в коде и в `docs/APP_IDEAS.md` ещё не записана. Ближайшие механизмы ходят с сервера XOS на чужие машины (SSH, Docker API, VNC, SQL, туннель) и явно не принимают адреса внутренних сетей.

### 1.2 Стек

|------|------|
| API | PHP 8.4, Symfony 7.4, Doctrine ORM 3, DBAL 3, миграции |
| Вход | Lexik JWT, gesdinet refresh-token, HttpOnly-cookie `xos_refresh` / `xos_app_refresh` |

Секреты задаются окружением: `APP_SECRET`, `JWT_PASSPHRASE`, `DATABASE_URL`, ключи шифрования токенов и SSH, параметры шлюза и Mercure. Список — в `README.md`.

Новый домен Samba встаёт в тот же шаблон, отдельный каркас приложения не нужен.

### 1.4 Модули

Защищённые модули перечислены дважды и должны совпадать: `server/src/App/Security/ProtectedAppModules.php` и `client/src/core/auth/protectedApps.ts`.

| Модуль | Роль входа | Назначение |
|--------|------------|------------|
| Main | `ROLE_MAIN` | Пользователи, группы, подразделения, каталог прав, журнал |
| Device | `ROLE_DEVICE` | Учёт техники, комплектующие, программы, лицензии |
| Explorer | `ROLE_EXPLORER` | Диски и файлы пользователя на диске XOS и в Яндекс.Диске |
| SchoolTask, IBlock, Recipe, IncCom, Calendar, Board, PKB, Inbox, Github, TeamStorm | свои `ROLE_*` | Предметные приложения стола |

| SSH | `ROLE_SSH` | Сохранённые подключения и терминал |

Права модуля описывает `setting.json`. Команда `php bin/console main:claimant:sync` переносит claimants и битовые `can_*` в БД. Проверка на запросе — атрибут `App\Attribute\Access` и `AccessSubscriber`: роль `ROLE_<модуль>` / `ROLE_<модуль>_ROOT` / `ROLE_ROOT` и битовая маска scope.

Привычки, стикеры и часть виджетов хранят состояние в user-data, своих таблиц нет.

### 1.5 Доступ к чужим машинам

Три независимых пути. Ни один не вызывает Samba и не читает `smb.conf`.

**SSH и шлюз.** Пользователь хранит подключение в `ssh_connection`: хост, порт, логин, пароль или ключ. Секрет шифруется `SshSecretCipher` (AES-256-GCM, префикс `enc:v1:`, ключ `SSH_SECRET_KEY`, иначе `APP_SECRET`). Терминал берёт билет `POST /api/ssh/gateway/ticket` (TTL 30 секунд, не больше трёх сессий на пользователя). Браузер открывает WebSocket шлюза. Шлюз вызывает `POST /api/ssh/gateway/redeem` с заголовком `X-Gateway-Secret` и получает расшифрованные пароль и приватный ключ, после чего сам открывает SSH. Файрвол `ssh_gateway` для `redeem` и `release` стоит с `security: false`. Без `SSH_GATEWAY_PUBLIC_URL` поток остаётся в PHP (`SshStream`). Рядом есть SFTP (`SftpBrowser`) — обход файлов по тому же исходящему SSH.

Хост проверяется в `SshConnectionPayload`: частные и зарезервированные IP, `localhost`, суффиксы `.local` и `.internal` отклоняются. Шлюз живёт в compose рядом с API, а не на управляемой машине.

**Ops.** Таблица `ops_link` — подключение одного пользователя. Поле `kind`: `db`, `docker`, `vnc`, `tunnel`.

| kind | Кто исполняет | Куда ходит |
|------|----------------|------------|
| `docker` | `Ops\Service\DockerApi` из процесса PHP | HTTP Docker Engine API 1.41: список, start/stop, хвост логов до 200 КБ |
| `vnc` | `VncClient` | Прямое TCP к хосту |
| `db` | `DbQuery` | SQL к MySQL или PostgreSQL с сохранённым паролем |
| `tunnel` | `TunnelRuntime` | Пишет ключ на диск XOS и запускает `ssh -N -L`, слушает только `127.0.0.1` |

Секреты Ops шифруются тем же `SshSecretCipher`. Хост для этих подключений проходит `Ops\Service\PublicHost` с тем же запретом внутренних адресов. Удаление пользователя каскадом удаляет и SSH-подключения, и ops-ссылки (`onDelete: CASCADE`).

**Проводник.** `Explorer\Entity\UserDisk` и `VolumeAdapterInterface`. Встроенные адаптеры — локальный каталог (`var/explorer/home`, `var/uploads`, `var/img`) и Яндекс.Диск. Общего SMB-адаптера нет. Файлы модулей (`Main\Entity\File`) лежат на диске XOS и отдаются через `/uploads` после проверки владельца.

Итог для будущего разреза: центр сам инициирует соединение, хранит обратимо зашифрованные секреты цели и не умеет дотянуться до типичного Samba-хоста во внутренней сети. Шлюз SSH — отдельный процесс, но это прокси терминала браузера, а не агент на сервере Samba.

`GET /api/health` отвечает `{"status":"ok"}` и ничего не знает о внешних хостах.

### 1.6 Модель данных, которая пересекается с задачей

**Идентичность приложения, не каталог AD.** `main_user` (логин, пароль Symfony, JSON-колонка `roles`, подразделение `ou_id`, признак блокировки). Группы `main_group` — дерево (`parent_id`). Подразделения `main_ou` плоские: кода родителя нет, это метка области видимости списков (`OuScope`), а не дерево LDAP. У пользователя есть свой `parent_id`, к оргструктуре домена он не относится. Роли Symfony (`ROLE_MAIN`, `ROLE_SSH`, `ROLE_ROOT`, …) и битовые scope из `setting.json` защищают API XOS. Журнал — `Main\Service\AuditLogger` (действие, тип сущности, id, краткий текст, JSON payload, пользователь).

**Учёт техники.** `Device` — карточка с типом, серийным номером, учётом, местом, программами и лицензиями. Поля «этот хост — Samba», адреса агента и признака онлайн нет. Список устройств активное подразделение не фильтрует.

**Подключения.** `ssh_connection` и `ops_link` принадлежат одному `main_user`. Это личные закладки, не реестр инфраструктуры организации.

Сущностей «сервер», «роль Samba», «шара», «домен AD», «агент» нет.

### 1.7 Вход людей

`POST /api/login` принимает логин и пароль, отдаёт access-токен в JSON. Refresh кладётся в HttpOnly-cookie и в JSON не возвращается (`RefreshCookieSubscriber`). `POST /api/token/refresh` обновляет пару. После перезагрузки страницы access в памяти нет, оболочка поднимает сессию cookie. Выход — `GET /api/logout`.

Файрволы stateless. У календаря, школы и IncCom есть отдельные файрволы для автономных окон. Ограничение входа — 5 попыток за 15 минут (в тесте лимит снят). Отдельный лимитер `public_api` стоит на регистрации, прокси браузера, refresh и загрузке файлов.

Машинной аутентификации нет: нет клиентских сертификатов, нет учётной записи агента, нет выпуска одноразового токена регистрации хоста. Единственный общий секрет процесса — `SSH_GATEWAY_SECRET`, и он общий на весь шлюз, а не на каждый хост.

### 1.8 Слово «роль» в текущем коде

В XOS роль — это роль человека в приложении (`ROLE_*`) или битовый scope. Роль процесса Samba (`server role` в `smb.conf`) нигде не моделируется. Один и тот же хост не может быть записан как файловый сервер, контроллер или их сочетание, потому что записи хоста нет.

Подразделение XOS нельзя принять за OU Active Directory: нет иерархии, нет SID, нет привязки к realm.

## 2. Предлагаемая архитектура

### 2.1 Решение

Samba добавляется новым контуром. Центр остаётся приложением XOS. На каждом хосте Samba работает один агент и сам подключается к XOS.

Существующие SSH, Ops и проводник не становятся транспортом Samba.

| Уже есть | Почему не транспорт Samba |
|----------|---------------------------|
| Исходящий SSH и Ops | Соединение открывает XOS. Частные адреса запрещены. Типичный DC стоит во внутренней сети и снаружи не виден |
| `ssh-gateway` | Стоит рядом с API, проксирует байты терминала, по общему секрету отдаёт расшифрованный пароль и ключ |
| Mercure | Подписчики доски. Канала команд и взаимной аутентификации хоста нет |
| `VolumeAdapterInterface` | Читает файлы на диске XOS или в Яндекс.Диске. Запись `smb.conf` и `samba-tool` сюда не ложатся |
| `main_user` / `main_group` / `main_ou` | Права приложения. Каталог AD — другой жизненный цикл, другие идентификаторы |

Один хост — один агент — один `smb.conf`. Два агента на одной машине будут переписывать один файл и одну базу `sam.ldb`.

### 2.2 Кто за что отвечает

**XOS (центр)**

- Реестр серверов, объявленные возможности, привязка к домену.
- Желаемое состояние (шары, узкий набор параметров, каталог домена, когда дойдут записи).
- Очередь команд, поколение конфигурации, результат, журнал через `AuditLogger`.
- Выпуск и отзыв учётных данных агента.
- Окна стола, `ROLE_SAMBA` и scope в `setting.json`.
- Политика версий протокола: какие агенты ещё принимаются.

Центр не запускает `samba-tool`, не пишет `smb.conf`, не хранит пароль администратора домена и не открывает порт 445.

**Агент (на хосте или рядом с ним, один на хост)**

- Исходящее соединение к XOS.
- Определение фактической роли Samba и состояния служб.
- Единственный на хосте писатель `smb.conf` и единственный вызывающий `samba-tool`.
- Исполнение только команд из белого списка, проверка `testparm` перед применением, возврат укороченного результата.
- Heartbeat.

Агент не рисует интерфейс, не хранит пользователей XOS и не ходит в MySQL центра.

### 2.3 Роли файлового сервера, DC и смешанный хост

В Samba директива `server role` одна на файл. Совмещение «и DC, и отдельный member» в одном `smb.conf` невозможно. Совмещение, которое реально нужно, другое: контроллер домена одновременно публикует файловые шары (SYSVOL, NETLOGON и обычные шары). Файловый сервер без домена — это `standalone server` или `member server`.

В продукте это набор возможностей плюс членство, а не один enum из трёх значений.

| Объявление в UI | Членство | Возможности | Смысл на хосте |
|-----------------|----------|-------------|----------------|
| Файловый сервер | `standalone` или `member` | `file` | Шары. Каталогом AD этот хост не владеет |
| Контроллер домена | `dc` | `dc` | Домен AD. Шары можно не вести |
| Оба | `dc` | `dc` и `file` | Тот же DC, плюс шары. Отдельный второй `smbd` не ставится |

Проверка при сохранении сервера отвергает невозможные сочетания: `dc` вместе с членством `member`; `file` без права править шары; второй агент на уже занятый `server_id`.

Объявленное и обнаруженное хранятся отдельно. Агент присылает фактический `server role` и версии пакетов. Расхождение показывается в карточке и блокирует команды, которые требуют отсутствующую возможность. Команду отклоняет и центр (до постановки в очередь), и агент (перед запуском).

Команды шар меняют только секции шар. Команды каталога AD идут через `samba-tool` и не переписывают `[global]`. Смена `server role`, provision и demote — отдельные операции со своим подтверждением. Пока такая операция не поставлена, агент отказывается применять конфиг, который меняет роль.

У хоста один счётчик поколения конфигурации. Команды, которые трогают диск Samba, сериализуются: агент берёт следующую только после результата предыдущей. Так смешанный хост не применяет шару и правку домена параллельно.

Домен — отдельная сущность (`dns name`, NetBIOS, realm). Первый DC её создаёт. Файловый `member` ссылается на уже известный домен. Несколько DC в одном домене на первых фазах можно завести в реестре, репликация и FSMO в объём этих фаз не входят: карточка показывает, что второй контроллер центром не синхронизируется.

Подразделение XOS (`ou_id` на сервере) — только метка «чья площадка» для списков. В LDAP оно не пишется.

### 2.4 Направление и протокол

Соединение открывает агент. Входящий порт на хосте Samba не нужен. Центр остаётся достижимым по HTTPS, хосты за NAT сами к нему подключаются.

Транспорт первой версии:

- HTTPS для регистрации и для разовых запросов.
- WebSocket поверх TLS (`wss`) как долгоживущий канал: hello, heartbeat, команды, результаты.
- Если путь WebSocket закрыт прокси, тот же конверт сообщений уходит длинным опросом HTTPS. Авторизация та же.

Конверт JSON, схема лежит в репозитории (раздел 2.11): версия протокола, id сообщения, id сервера, вид (`hello`, `heartbeat`, `command`, `result`, `event`), требуемая возможность, ключ идемпотентности, поколение.

gRPC как вход в Symfony не предлагается. В проекте нет gRPC-сервера, API и файрволы — HTTP. Отдельный ingress имел бы смысл после того, как схема сообщений устоится. До этого JSON-схема не привязана к кадру WebSocket, и сменить несущий протокол можно без смены команд.

Mercure остаётся каналом браузера доски. Статус агентов в окна можно позже публиковать туда уже после того, как центр принял heartbeat. Команды через хаб Mercure не ходят.

### 2.5 Регистрация и аутентификация агента

Учётные данные агента не равны JWT человека и не равны `SSH_GATEWAY_SECRET`.

1. Администратор с `ROLE_SAMBA` создаёт сервер и получает одноразовый секрет регистрации. В БД лежит только хеш (штатный password hasher Symfony). Срок — минуты, использование однократное. Повторный показ невозможен.
2. На хосте агент один раз вызывает `POST /api/samba/enroll`: секрет, имя хоста, обнаруженная роль, при выбранном режиме — CSR.
3. Центр помечает секрет использованным и привязывает агента к `server_id`.
4. Дальше канал живёт на отдельном файрволе `samba_agent` (шаблон сборки — `server/config/packages/security.php`). Файрвол проверяет подлинность агента. Режим `security: false`, как у `ssh_gateway`, сюда не переносится.
5. Действия человека остаются на файрволе `api` с пользовательским JWT. Человек секрет агента по каналу команд не шлёт.

Предпочтительная подлинность канала — mTLS: центр выступает непубличным CA и подписывает клиентский сертификат на `server_id`. Ключ остаётся на хосте, права файла `0600`. Отзыв — по серийному номеру, повторная регистрация гасит предыдущий сертификат.

Допустимый первый срез, если mTLS откладывается на фазу 6: случайный секрет агента, в БД только хеш, заголовок `Authorization` только на файрволе агента, поворот секрета из карточки сервера. Обратимое шифрование в духе `SshSecretCipher` для этого секрета не используется: центр должен уметь проверить секрет, а не восстановить его.

Истечение регистрации, повторное использование и чужой `server_id` отвечают отказом без тела конфигурации.

### 2.6 Команды

Источник правды для шар и узких параметров хоста — желаемое состояние в MySQL. Команда — переход к следующему поколению, а не произвольный сценарий оболочки.

Состояния команды: `queued`, `delivered`, `running`, `succeeded`, `failed`, `rejected`, `expired`. Повтор с тем же ключом идемпотентности возвращает уже известный результат.

Белый список по возможностям (имена операций, без произвольной строки shell):

| Возможность | Операции |
|-------------|----------|
| `file` | прочитать действующие шары, применить список шар, удалить шару, `testparm`, краткий `smbstatus` |
| `dc` | сведения о домене, чтение и запись пользователей, групп и OU каталога, чтение записей DNS домена |
| обе | тот же агент; каждая команда помечена требуемой возможностью |

Агент запускает разрешённые программы списком аргументов, без оболочки. Вывод обрезается по размеру (ориентир уже есть у Docker-логов Ops — 200 КБ). Ненулевой код и провал `testparm` переводят команду в `failed`, поколение не увеличивается, предыдущий файл конфигурации остаётся.

Provision домена и смена `server role` в этот список сами не входят. Это отдельные операции карточки: явное подтверждение, запись в аудит, на хосте — снимок конфигурации силами агента до запуска.

Пароль администратора домена в очередь не кладётся. Агент действует локальными правами службы. Если операция требует учётных данных, они вводятся на хосте при установке агента и в XOS не уезжают.

Кто поставил команду, пишется в `AuditLogger`: пользователь XOS, id сервера, тип, id команды. В payload не попадают секреты и пароли.

### 2.7 Состояние и здоровье

Интервал heartbeat — порядка 30 секунд. В нём: версия агента, версия протокола, hostname, версия пакетов Samba, обнаруженный `server role`, состояние юнитов (`smbd`, `samba` / `samba-ad-dc`, `winbind` — какие есть), расхождение часов, свободное место на томе данных Samba, последнее применённое поколение.

Три пропущенных интервала переводят сервер в `stale`, дальше — в `offline`. Центр сам на 445 и 22 не опрашивает. `GET /api/health` по-прежнему означает «жив процесс PHP», а не «жив DC».

В карточке видны объявленные возможности, обнаруженная роль и поколение. Расхождение роли — отдельный признак, оно не затирает объявление молча.

### 2.8 Версии

`hello` называет версию протокола. Центр принимает текущую и предыдущую. Команда новее, чем понимает агент, возвращается как `rejected` и остаётся в очереди до обновления агента или отмены. Версия пакетов Samba хранится на сервере и показывается в UI. У операции может быть минимальная версия агента.

Релиз агента нумеруется отдельно от стола: хосты обновляются не в тот же момент, что контейнер `app`.

### 2.9 Безопасность

Опора на то, что уже болит в коде, и на то, что агент будет корневым по отношению к домену.

- Компрометация центра или секрета регистрации равна компрометации домена на подключённых хостах. Секрет регистрации одноразовый, канал агента отдельно от сессии человека, секрет агента в БД только в виде хеша.
- `redeem` SSH сейчас отдаёт пароль и приватный ключ процессу с общим заголовком. Для Samba такой обмен не повторяется.
- `DbQuery` выполняет SQL, который сформулировал центр. У агента нет операции «выполни строку».
- `TunnelRuntime` пишет приватный ключ на диск XOS. Агент не присылает в центр ключи хоста и пароли домена.
- Запрет частных адресов в SSH и Ops — защита XOS от походов во внутреннюю сеть. Её снимать, чтобы дотянуться до DC, не нужно: соединение исходящее со стороны агента.
- IP агента не считается удостоверением. `SYMFONY_TRUSTED_PROXIES` влияет на видимый адрес, криптографическая проверка — нет.
- Повторная регистрация отзывает прежние учётные данные. Отключённый сервер команды не получает.
- Часы: агент сообщает перекос времени. Для Kerberos это признак карточки, не молчаливый успех.
- Один писатель `smb.conf`. Смена роли и provision не проходят через обычное применение шар.
- Журнал команд хранит типы и итоги, не тела паролей.
- На канал агента — свой лимит частоты, не общий `public_api` браузера.
- Служба агента на хосте ограничивается правами, которых хватает на `smb.conf`, перезагрузку конфигурации и `samba-tool`. Шире, чем этот список, unit не получает.

Исторические файлы окружения в git (их фиксирует `docs/PLAN.md`) для контура, который держит домен, опаснее, чем для стола. Ротация тех секретов — отдельное решение владельца и в эти фазы не входит. В новый модуль секреты домена не записываются.

### 2.10 Что куда относится

Переносить нечего: прикладного Samba нет. Ниже — куда класть новое и что не трогать.

| Код | Куда |
|-----|------|
| Стол, Main, Device, Explorer, прикладные модули, SSH, Ops, `ssh-gateway`, Mercure | Остаются в XOS как есть |
| `server/src/Samba/` — сущности, API человека, API агента, очередь, проверка схемы | Новый модуль центра |
| `server/src/Samba/setting.json`, строка в `ProtectedAppModules` и `protectedApps.ts` | Тот же модуль, чтобы сработали claimant и «Пуск» |
| Файрвол `samba_agent` в сборке `security.php` | Центр |
| `client/src/apps/samba-*`, `client/src/features/samba` | Окна реестра, шар и домена |
| `agent/` — процесс, systemd, схема сообщений | Хост Samba |
| Вызовы `samba-tool`, правка `smb.conf`, `testparm` | Только `agent/` |
| Пароли и ключи `ssh_connection` / `ops_link` | Не читаются агентом и не используются как регистрация |

Связь с учётом техники — необязательная ссылка `device_id` на карточке сервера, когда это понадобится. Сливать `Device` и сервер Samba в одну таблицу не стоит: у карточки техники другой срок жизни (списание, комплектующие, лицензии).

Проводник на первых фазах шары Samba не показывает. Обзор шары через агента — отдельное решение после того, как применение конфига уже работает. Домашний каталог `home://` остаётся на диске XOS.

Пользователи домена не пишутся в `main_user`. Иначе права стола и пароли AD окажутся одной таблицей, а удаление учётной записи приложения снесёт человека в домене или наоборот.

### 2.11 Репозиторий

Оставляем один репозиторий. Рядом уже лежат `client`, `server` и `ssh-gateway`, а схема сообщений должна меняться одним коммитом с API, который её проверяет.

```
agent/
  protocol/messages.schema.json
  xos_agent/          # процесс: соединение, heartbeat, исполнитель белого списка
  systemd/xos-agent.service
server/src/Samba/
  Entity/  Controller/  Service/  config/  setting.json
client/src/apps/samba-servers/   # и далее окна по фазам
client/src/features/samba/
docs/architecture-split.md
```

Схему читают оба конца. Агент на неё опирается напрямую. PHP валидирует тот же файл и не отдаёт агенту свои классы Doctrine.

Язык агента первой версии — Python 3: на хосте Samba он уже есть вместе с `samba-tool`, аргументы собираются списком, оболочка не вызывается. Отдельный статический бинарник имеет смысл, когда появится свой конвейер пакетов; до этого второй язык в репозитории не нужен.

Свой git-репозиторий агента оправдан, когда появятся пакет (deb) и цикл выпуска, не совпадающий с контейнером стола. До фаз 2–3 это только разъедет схему. `ssh-gateway` показывает, что второй рантайм в этом репозитории уже принят, и одновременно показывает удачный объём: маленький процесс со своим `package.json`, без доступа к доменным секретам центра. Объём агента тот же, полномочия — строже.

В CI агент на фазе 1 не обязан поднимать Samba. Контракт проверяется схемой и PHPUnit очереди. Исполнитель на фазе 2 покрывается тестом с подставной командой, без `smbd`.

### 2.12 Фазы

Каждая фаза выкладывается отдельно. Предыдущая продолжает работать. Вырезать старый Samba-код не потребуется.

**Фаза 0.** Этот документ.

**Фаза 1. Реестр в центре.** Таблицы сервера, домена, одноразовой регистрации. `ROLE_SAMBA`, `setting.json`, пункт в обоих списках защищённых модулей, окно списка и карточки. Команд и процесса агента нет. Готово, когда API сохраняет три допустимых объявления (файл, DC, оба) и отвергает `dc` вместе с членством `member`.

**Фаза 2. Связь.** Процесс агента: регистрация, `hello`, heartbeat, обнаруженная роль. Очередь изменений пустая. Файрвол `samba_agent`. Готово, когда хост с частным адресом виден в карточке как online без входящего порта и без записи в `ssh_connection`.

**Фаза 3. Шары.** Желаемый список шар, команды `file`, поколение, `testparm` на агенте. Готово, когда правка шары на standalone и на DC не меняет `server role` и не пишет в `sam.ldb`.

**Фаза 4. Чтение AD.** С DC читаются сведения о домене, пользователи и группы. Записи `main_user` не создаются. Готово, когда карточка DC показывает каталог, а карточка чистого файлового сервера эту команду даже не ставит в очередь.

**Фаза 5. Запись AD и член в домене.** Запись пользователей и групп, присоединение `member` к домену, который уже есть в реестре. Смешанный хост держит одну очередь. Provision — отдельная подтверждённая операция. Готово, когда две команды одного сервера не исполняются параллельно, а аудит называет пользователя XOS и id команды.

**Фаза 6. Канал.** mTLS и отзыв, если фаза 2 вышла на хешированном секрете. Поворот учётных данных с карточки. Готово, когда секрет прошлой регистрации и предыдущий сертификат получают отказ.

Вне этих фаз: репликация нескольких DC, обзор шар в проводнике, перенос Docker/VNC/SQL на тот же агент, синхронизация `main_user` с AD, пакетный репозиторий агента.

## 3. Вопросы и риски

Решения владельца, без которых фазу 1 лучше не начинать.

1. **Стол или отдельная консоль.** Код — рабочий стол с окнами. Управление доменом можно вести теми же окнами (`samba-servers` в «Пуске») или отдельным входом. От этого зависит только клиент; агент и очередь общие. По умолчанию в этом проекте — окна стола, потому что так устроены SSH и Ops.
2. **Какой Samba.** Нужна опора на AD DC (`server role = active directory domain controller`) и явный отказ от classic NT4 DC. Иначе модель членства разъедется.
3. **Один домен на установку XOS или несколько.** От этого зависит, одна ли сущность домена обязательна в фазе 1.
4. **Каталог людей.** `main_user` остаётся учётом входа в XOS. Пользователи AD живут в своих таблицах и появляются не раньше фазы 4. Подтвердить, что синхронизация «группа XOS → группа домена» не требуется. Подразделения XOS плоские и в LDAP не копируются.
5. **Смешанный хост.** В этом документе «оба» значит DC, который ещё и отдаёт шары, один процесс Samba. Подтвердить, что отдельный второй экземпляр Samba на том же сервере не нужен.
6. **Подлинность агента на фазе 2.** mTLS сразу или хеш секрета и mTLS на фазе 6. Второе короче до первого heartbeat, первое меньше похоже на `X-Gateway-Secret`.
7. **Язык и упаковка агента.** Здесь предложен Python в каталоге `agent/` этого репозитория. Отдельный репозиторий и deb — после того, как схема переживёт фазы 2–3.
8. **Ops на том же агенте.** Docker, VNC, SQL и туннель остаются как есть. Переносить их на агент хоста — другой проект: у них модель «личное подключение пользователя», у Samba — реестр организации.
9. **Владелец записи сервера.** Запись инфраструктурная. Её нельзя вешать на `user_id` с `ON DELETE CASCADE`, как `ssh_connection` и `ops_link`: удаление человека снесло бы DC из реестра. Достаточно `created_by` и прав `ROLE_SAMBA`. Нужно ли дополнительно резать видимость по `main_ou`.
10. **Хост offline.** Команды копятся до `expired` или сразу отвергаются. Для шар накопление уместно в пределах одного поколения. Для provision — только немедленный отказ, если агент не online.
11. **Уже стоящие серверы.** Есть ли парк с готовым доменом, который агент должен только читать (фаза 4 до фазы 5), или первый DC будет создаваться из XOS.
12. **Куда агент подключается.** Нужен стабильный HTTPS-адрес XOS, достижимый с площадок. Если сам центр за NAT без входящего адреса, потребуется точка публикации. Текущий compose публикует `app` на 8080 и шлюз на 7681, агентского входа нет.
13. **Часы и DNS.** Берёт ли центр на себя проверку времени и записи DNS домена, или на фазах 4–5 это только чтение и предупреждение в карточке.
14. **Срок хранения журнала команд** и кто, кроме `ROLE_SAMBA`, его читает. Рядом уже есть `main.audit`.

Риски, которые фазы не снимают сами:

- Агент по сути администратор хоста. Ошибка белого списка опаснее ошибки в окне задач.
- Второй DC без проекта репликации создаёт ложное чувство, что домен резервирован.
- Общая очередь с Ops или общий секрет со шлюзом SSH снова приведёт к тому, что пароль домена окажется в MySQL в обратимом виде.
- Provision портит существующий хост. Пока операция не вынесена из обычного применения шар, её нельзя включать.
- Исторические секреты в git становятся границей доверия всей схемы, как только к XOS подключат боевой DC.
