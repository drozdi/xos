# Разделение XOS и агента Samba

Версия 2. Дата: 2026-11-13. База: `7070dbf` на `master`. Это только план: код, ветки и PR не создаются.

Что изменилось относительно версии 1: открытые вопросы закрыты решениями владельца (раздел 3), под них переписаны архитектура, модель данных, агент, безопасность и фазы. В правке от 13.11 закрыты и четыре оставшихся вопроса: TLS завершается на Apache, пароли AD, отключение вместо удаления, хранение журнала 7 дней. Раздел 1 (как устроен проект сейчас) почти не менялся, в него добавлены факты, которые понадобились для новых решений.

По репозиторию нет прикладного Samba: поиск `samba`, `smb.conf`, `samba-tool`, `winbind`, `krb5`, `netbios` в PHP, TypeScript, YAML и Markdown ничего не даёт. Управлять файловым сервером и контроллером домена сейчас нечем. Ниже — что реально собрано, какой из существующих механизмов годится как образец, и как разрезать систему на центральное приложение и агент на каждом хосте Samba.

## 1. Текущий проект

### 1.1 Назначение

XOS — рабочий стол в браузере. Пользователь входит, видит стол, «Пуск» и окна приложений. Данные приложений лежат в MySQL и доступны после входа с другого устройства. Оболочка не знает предметных правил модулей. Модуль не рисует стол и не хранит геометрию окон (`docs/TZ.md`).

Идея владельца — централизованно управлять серверами Samba в роли контроллера домена AD, которые могут ещё и раздавать шары, — в коде и в `docs/APP_IDEAS.md` ещё не записана. Ближайшие механизмы ходят с сервера XOS на чужие машины (SSH, Docker API, VNC, SQL, туннель) и явно не принимают адреса внутренних сетей.

### 1.2 Стек

| Слой | Факт |
|------|------|
| API | PHP 8.4, Symfony 7.4, Doctrine ORM 3, DBAL 3, миграции |
| Вход | Lexik JWT, gesdinet refresh-token, HttpOnly-cookie `xos_refresh` / `xos_app_refresh` |
| Данные | MySQL 8 в проде и Docker; тесты — SQLite из `.env.test` |
| Клиент | React 19, Vite, Mantine 9, TanStack Query, Zustand |

| Сборка | multi-stage `Dockerfile` (Node → Composer → `php:8.4-apache`), `docker-compose.yml`: `app`, `mysql`, `mercure`, `ssh-gateway` |

Секреты задаются окружением: `APP_SECRET`, `JWT_PASSPHRASE`, `DATABASE_URL`, ключи шифрования токенов и SSH, параметры шлюза и Mercure. Список — в `README.md`.

Новый домен Samba встаёт в тот же шаблон, отдельный каркас приложения не нужен.

### 1.4 Модули

Защищённые модули перечислены дважды и должны совпадать: `server/src/App/Security/ProtectedAppModules.php` и `client/src/core/auth/protectedApps.ts`.

| Модуль | Роль входа | Назначение |
|--------|------------|------------|
| Main | `ROLE_MAIN` | Пользователи, группы, подразделения, каталог прав, журнал |
| Device | `ROLE_DEVICE` | Учёт техники, комплектующие, программы, лицензии |
| Explorer | `ROLE_EXPLORER` | Диски и файлы пользователя на диске XOS и в Яндекс.Диске |
| SchoolTask, IBlock, Recipe, IncCom, Calendar, Board, PKB, Inbox, Github, TeamStorm | свои `ROLE_*` | Предметные приложения стола |
| Todo | достаточно входа | Списки задач, модуль не в списке защищённых |
| SSH | `ROLE_SSH` | Сохранённые подключения и терминал |
| Ops | отдельной роли нет, контроллеры помечены `#[Access('ssh')]` | Docker, VNC, SQL, SSH-туннель. В `ProtectedAppModules` нет |

Права модуля описывает `setting.json`. Команда `php bin/console main:claimant:sync` переносит claimants и битовые `can_*` в БД. Проверка на запросе — атрибут `App\Attribute\Access` и `AccessSubscriber`: роль `ROLE_<модуль>` / `ROLE_<модуль>_ROOT` / `ROLE_ROOT` и битовая маска scope.

Привычки, стикеры и часть виджетов хранят состояние в user-data, своих таблиц нет.

Раздел «Администрирование» в «Пуске» уже есть: группа `admin` в `client/src/core/taskbar/startMenu/defaults.ts` (сортировка 0, первая в меню) и в `client/src/core/taskbar/groupLabels.ts`. Туда попадают окна Main: `createMainListManifestOptions` в `client/src/features/main/mainAppUtils.ts` ставит `startMenuGroup: 'admin'`. SSH и Ops лежат в группе `manage` («Управление»).

### 1.5 Доступ к чужим машинам

Три независимых пути. Ни один не вызывает Samba и не читает `smb.conf`.

**SSH и шлюз.** Пользователь хранит подключение в `ssh_connection`: хост, порт, логин, пароль или ключ. Секрет шифруется `SshSecretCipher` (AES-256-GCM, префикс `enc:v1:`, ключ `SSH_SECRET_KEY`, иначе `APP_SECRET`). Терминал берёт билет `POST /api/ssh/gateway/ticket` (TTL 30 секунд, не больше трёх сессий на пользователя). Браузер открывает WebSocket шлюза. Шлюз вызывает `POST /api/ssh/gateway/redeem` с заголовком `X-Gateway-Secret` и получает расшифрованные пароль и приватный ключ, после чего сам открывает SSH. Файрвол `ssh_gateway` для `redeem` и `release` стоит с `security: false`. Без `SSH_GATEWAY_PUBLIC_URL` поток остаётся в PHP (`SshStream`). Рядом есть SFTP (`SftpBrowser`) — обход файлов по тому же исходящему SSH.

Хост проверяется в `SshConnectionPayload`: частные и зарезервированные IP, `localhost`, суффиксы `.local` и `.internal` отклоняются. Шлюз живёт в compose рядом с API, а не на управляемой машине.

**Ops.** Таблица `ops_link` — подключение одного пользователя. Поле `kind`: `db`, `docker`, `vnc`, `tunnel`.

| kind | Кто исполняет | Куда ходит |
|------|----------------|------------|
| `docker` | `Ops\Service\DockerApi` из процесса PHP | HTTP Docker Engine API 1.41: список, start/stop, хвост логов до 200 КБ |
| `vnc` | `VncClient` | Прямое TCP к хосту |
| `db` | `DbQuery` | SQL к MySQL или PostgreSQL с сохранённым паролем |
| `tunnel` | `TunnelRuntime` | Пишет ключ на диск XOS и запускает `ssh -N -L`, слушает только `127.0.0.1` |

Секреты Ops шифруются тем же `SshSecretCipher`. Хост для этих подключений проходит `Ops\Service\PublicHost` с тем же запретом внутренних адресов. Удаление пользователя каскадом удаляет и SSH-подключения, и ops-ссылки (`onDelete: CASCADE`).

**Проводник.** `Explorer\Entity\UserDisk` и `VolumeAdapterInterface`. Встроенные адаптеры — локальный каталог (`var/explorer/home`, `var/uploads`, `var/img`) и Яндекс.Диск. Общего SMB-адаптера нет. Файлы модулей (`Main\Entity\File`) лежат на диске XOS и отдаются через `/uploads` после проверки владельца.

Итог для будущего разреза: центр сам инициирует соединение, хранит обратимо зашифрованные секреты цели и не умеет дотянуться до типичного Samba-хоста во внутренней сети. Шлюз SSH — отдельный процесс, но это прокси терминала браузера, а не агент на сервере Samba.

`GET /api/health` отвечает `{"status":"ok"}` и ничего не знает о внешних хостах.

### 1.6 Модель данных, которая пересекается с задачей

**Идентичность приложения, не каталог AD.** `main_user` (логин, пароль Symfony в виде хеша, ФИО, `email`, `phone`, `description`, флаги `active` и `loocked`, срок `active_from` / `active_to`, версия строки `x_timestamp` под `ORM\Version`, JSON-колонка `roles`, подразделение `ou_id`). Группы `main_group` — дерево (`parent_id`), членство — отдельная сущность `UserGroup`. Подразделения `main_ou` плоские: кода родителя нет, это метка области видимости списков (`OuScope`), а не дерево LDAP. У пользователя есть свой `parent_id`, к оргструктуре домена он не относится. Роли Symfony (`ROLE_MAIN`, `ROLE_SSH`, `ROLE_ROOT`, …) и битовые scope из `setting.json` защищают API XOS. Журнал — `Main\Service\AuditLogger` (действие, тип сущности, id, краткий текст, JSON payload, пользователь).

**Учёт техники.** `Device` — карточка с типом, серийным номером, учётом, местом, программами и лицензиями. Поля «этот хост — Samba», адреса агента и признака онлайн нет. Список устройств активное подразделение не фильтрует.

**Подключения.** `ssh_connection` и `ops_link` принадлежат одному `main_user`. Это личные закладки, не реестр инфраструктуры организации.

Сущностей «сервер», «роль Samba», «шара», «домен AD», «агент» нет.

### 1.7 Вход людей

`POST /api/login` принимает логин и пароль, отдаёт access-токен в JSON. Refresh кладётся в HttpOnly-cookie и в JSON не возвращается (`RefreshCookieSubscriber`). `POST /api/token/refresh` обновляет пару. После перезагрузки страницы access в памяти нет, оболочка поднимает сессию cookie. Выход — `GET /api/logout`.

Файрволы stateless. У календаря, школы и IncCom есть отдельные файрволы для автономных окон. Ограничение входа — 5 попыток за 15 минут (в тесте лимит снят). Отдельный лимитер `public_api` стоит на регистрации, прокси браузера, refresh и загрузке файлов.

Машинной аутентификации нет: нет клиентских сертификатов, нет учётной записи агента, нет выпуска одноразового токена регистрации хоста. Единственный общий секрет процесса — `SSH_GATEWAY_SECRET`, и он общий на весь шлюз, а не на каждый хост.

### 1.8 Слово «роль» в текущем коде

В XOS роль — это роль человека в приложении (`ROLE_*`) или битовый scope. Роль процесса Samba (`server role` в `smb.conf`) нигде не моделируется. Один и тот же хост не может быть записан как файловый сервер, контроллер или их сочетание, потому что записи хоста нет.

Подразделение XOS нельзя принять за OU Active Directory: нет иерархии, нет SID, нет привязки к realm.

## 2. Предлагаемая архитектура

### 2.1 Решение

Управление Samba — новое приложение XOS в разделе «Администрирование». На каждом сервере Samba стоит один агент на PHP. Агент сам подключается к XOS по адресу вида `https://xos.h1n.ru`, входящий порт на сервере не нужен.

Основные решения:

| Тема | Решение |
|------|---------|
| Где живёт интерфейс | Окна стола в группе `admin` («Администрирование») |
| Роль Samba | `server role = active directory domain controller`. Классический домен NT4 в модели предусмотрен как будущее значение, в фазы не входит |
| Серверы и домены | Подключается сколько угодно серверов, у них могут быть разные домены |
| Смешанный хост | Один процесс Samba: DC, который ещё и раздаёт шары. Второго экземпляра Samba на сервере нет |
| Каталог `main_*` | Отдельную запись (пользователь, группа, подразделение) можно привязать к нескольким доменам. Изменение записи уходит на все привязанные домены |
| Доступ | Личное подключение: сервер принадлежит пользователю `main_user` с ролью `ROLE_SAMBA`. Владелец может выдать доступ другим |
| Журнал команд | Читает только владелец сервера. Хранится 7 дней, срок настраивается |
| TLS | Завершается на Apache внутри `app` (`php:8.4-apache`, `mod_ssl`) |
| Агент | PHP, каталог `server/agent/` в этом репозитории, установка скриптом `install.sh`, настройка файлом. Без deb и отдельного репозитория |
| Подлинность агента | Хеш секрета с фазы 2, mTLS на фазе 6 |
| Сервер offline | Все команды копятся до восстановления связи, включая provision |
| Существующие серверы | Пока не подключаются. Первый DC создаётся из XOS через агент |
| Время | XOS проверяет часы сервера с учётом часового пояса |

Существующие SSH, Ops и проводник не становятся транспортом Samba и остаются как есть.

| Уже есть | Почему не транспорт Samba |
|----------|---------------------------|
| Исходящий SSH и Ops | Соединение открывает XOS. Частные адреса запрещены. Типичный DC стоит во внутренней сети и снаружи не виден |
| `ssh-gateway` | Стоит рядом с API, проксирует байты терминала, по общему секрету отдаёт расшифрованный пароль и ключ |
| Mercure | Подписчики доски. Канала команд и взаимной аутентификации хоста нет |
| `VolumeAdapterInterface` | Читает файлы на диске XOS или в Яндекс.Диске. Запись `smb.conf` и `samba-tool` сюда не ложатся |

Модель доступа при этом взята у SSH и Ops: сервер — личное подключение пользователя, а не общий реестр организации. Отличие одно, но важное: запись сервера нельзя удалять каскадом вместе с пользователем (раздел 2.4).

### 2.2 Кто за что отвечает

**XOS (центр)**

- Приложение в «Администрировании»: список серверов, карточка сервера, домены, шары, привязки каталога, журнал.
- Реестр серверов и доменов, владельцы и выданные доступы.
- Желаемое состояние: шары, привязки записей `main_*` к доменам, параметры provision.
- Очередь команд, поколение конфигурации, результаты, журнал команд.
- Отслеживание изменений `main_user`, `main_group`, `main_ou` и членства и постановка команд синхронизации.
- Выпуск и отзыв учётных данных агента, раздача `install.sh` и архива агента.
- Проверка времени и часового пояса по данным heartbeat.

Центр не запускает `samba-tool`, не пишет `smb.conf`, не открывает порт 445 и не хранит пароли домена в открытом или обратимо зашифрованном виде.

**Агент (один на сервер)**

- Исходящее соединение к XOS.
- Чтение локального файла настроек, локальные ограничения (какие каталоги можно отдавать шарами и т. п.).
- Определение фактического состояния: установлен ли Samba, выполнен ли provision, какой `server role`, состояние служб, время и часовой пояс.
- Единственный на хосте писатель `smb.conf` и единственный вызывающий `samba-tool`.
- Исполнение команд из белого списка, проверка предусловий перед запуском, `testparm` перед применением, возврат укороченного результата.
- Heartbeat.

Агент не рисует интерфейс, не хранит пользователей XOS и не ходит в MySQL центра.

### 2.3 Роль сервера и смешанный хост

Роль одна — AD DC. Отдельного файлового сервера без домена (`standalone`) и рядового члена домена (`member`) в этих фазах нет. Шары — дополнительная возможность того же DC.

| Объявление в UI | `server role` | Возможности | Смысл на хосте |
|-----------------|---------------|-------------|----------------|
| Контроллер домена | `active directory domain controller` | `dc` | Домен AD, шар кроме SYSVOL и NETLOGON нет |
| Контроллер домена с шарами | то же | `dc`, `file` | Тот же DC и тот же процесс `samba`, плюс секции шар в том же `smb.conf` |
| NT4 (позже) | `classic primary domain controller` | `nt4` | Значение зарезервировано в enum, API его пока отвергает |

Отдельный второй экземпляр Samba не нужен и не поддерживается. На DC служба `samba` (юнит `samba-ad-dc` в Debian и Ubuntu) сама запускает `smbd` для шар. Так же устроен Zentyal: один процесс Samba в роли AD DC, обычные шары описаны в том же `smb.conf`. Два процесса на одном хосте спорили бы за порты 445 и 139, за `smb.conf` и за `sam.ldb`.

Особенности шар на DC, которые агент учитывает:

- Права на шары — Windows ACL (`vfs_acl_xattr` на DC включён по умолчанию). Агент выставляет владельца и ACL через `samba-tool ntacl` или `setfacl`, а не через `chmod`.
- На DC сопоставление SID и uid/gid идёт через `idmap.ldb`, а не через `winbind` с диапазонами, как на рядовом члене домена. UI не показывает числовые uid.
- Шары с данными пользователей лучше держать на отдельном томе. Агент сообщает свободное место на томе шар в heartbeat.

Объявленное и обнаруженное хранятся отдельно. Агент присылает фактический `server role` и версии пакетов. Расхождение показывается в карточке и блокирует команды, которым нужна отсутствующая возможность. Команду отклоняет и центр (до постановки в очередь), и агент (перед запуском).

У хоста один счётчик поколения конфигурации и одна очередь. Команды исполняются строго по одной: агент берёт следующую только после результата предыдущей. Поэтому смешанный хост не применяет шару и правку домена параллельно.

### 2.4 Владелец и доступ

Сервер — личное подключение пользователя, как `ssh_connection` и `ops_link`.

- Открыть приложение может только пользователь `main_user` с ролью `ROLE_SAMBA` (или `ROLE_SAMBA_ROOT` / `ROLE_ROOT` по общим правилам `AccessSubscriber`).
- Создатель сервера становится владельцем (`owner_id`).
- Владелец выдаёт доступ к своему серверу другим пользователям с `ROLE_SAMBA`. Права доступа — битовая маска.
- Без роли `ROLE_SAMBA` выданный доступ не действует, но и не удаляется: вернули роль — доступ вернулся.
- Резать видимость по `main_ou` не нужно: видимость задают владелец и выданные доступы.

| Право | Что даёт | Владелец | Получатель доступа |
|-------|----------|----------|--------------------|
| `view` | Карточка, состояние, время, список шар и привязок | да | по выдаче |
| `shares` | Правка шар | да | по выдаче |
| `directory` | Привязка записей `main_*` к домену этого сервера | да | по выдаче |
| `provision` | Provision домена, перезапуск служб | да | по выдаче |
| `manage` | Поворот секрета агента, отключение сервера, выдача доступа | да | нет |
| `log` | Чтение журнала команд | да | нет, никогда |
| `transfer` | Передача владения | да | нет |

`log` нельзя выдать: журнал команд читает только текущий владелец. Даже `ROLE_ROOT` журнал через API не получает. В `main.audit` (общий журнал `AuditLogger`, его читают администраторы Main) пишутся только события уровня сервера без деталей команд: создан, удалён, передан, выдан или отозван доступ.

Когда владение передаётся, журнал переходит к новому владельцу вместе с сервером. Прежний владелец его больше не видит.

**Риск: удаление пользователя.** У `ssh_connection` и `ops_link` внешний ключ на пользователя с `ON DELETE CASCADE`. Если сделать так же, удаление владельца снесёт DC из реестра, очередь, привязки домена и журнал, хотя сам домен продолжит работать. Рекомендация: `owner_id` с `ON DELETE RESTRICT`. Удаление пользователя, у которого есть серверы, отклоняется с понятным сообщением: «сначала передайте серверы». Передать чужой сервер может `ROLE_SAMBA_ROOT` или `ROLE_ROOT`, это пишется в `main.audit`. Обычный путь ухода сотрудника — блокировка (`active = false`); у заблокированного владельца серверы продолжают работать, а очередь — исполняться. Выданные доступы (`samba_server_access`) удаляются вместе с получателем каскадом: это просто выдача, её потеря ничего не ломает.

### 2.5 Домены и каталог `main_*`

**Домены.** Домен — отдельная сущность: DNS-имя, realm, NetBIOS-имя, базовый DN, SID домена (приходит от агента). Домен появляется в реестре после provision на первом DC. Домены разных серверов независимы. Два сервера в одном домене (второй DC через `samba-tool domain join`) в эти фазы не входят. Если это появится, у домена будет назначенный сервер для записи каталога (`write_server_id`), а репликацию делает сама Samba.

Домен принадлежит владельцу сервера, на котором его создали. Привязывать к домену записи каталога может владелец или пользователь с правом `directory` на этом сервере.

**Привязка записей.** Запись `main_user`, `main_group` или `main_ou` можно привязать к одному или нескольким доменам. Для каждой пары «запись — домен» хранится строка привязки. XOS — источник правды для привязанных полей: изменение записи в окнах Main уходит на все домены, к которым она привязана.

| Запись XOS | Объект AD | Что синхронизируется |
|------------|-----------|----------------------|
| `main_user` | пользователь | `login` → `sAMAccountName` и `userPrincipalName` (`login@realm`); `first_name` → `givenName`; `second_name` → `sn`; `patronymic` → `middleName`; `alias` или ФИО → `displayName`; `email` → `mail`; `phone` → `telephoneNumber`; `description`; `active` и `loocked` → флаг отключения в `userAccountControl`; `active_to` → `accountExpires`; `ou_id` → контейнер, если это подразделение тоже привязано к домену |
| `main_group` | глобальная группа безопасности | имя → `cn` и `sAMAccountName`, описание |
| `UserGroup` (членство) | `member` группы | только если и пользователь, и группа привязаны к этому домену |
| `main_ou` | OU | имя. Подразделения XOS плоские, поэтому в домене они создаются одним уровнем внутри базовой OU домена (например `OU=XOS,DC=…`) |

Дерево `main_group` (`parent_id`) на первом шаге во вложенные группы не превращается: каждая группа плоская. Вложенность можно добавить позже флагом домена.

Объект AD после создания запоминается по `objectGUID`. Поэтому смена логина в XOS — переименование в AD (`samba-tool user rename`), а не новый пользователь.

**Как изменения доходят до серверов.**

1. Слушатель Doctrine в модуле Samba (`onFlush`) видит изменение привязанной записи `main_*` или членства. Модуль Main о Samba не знает.
2. На каждую привязку ставится задача синхронизации с ключом слияния вида `user:42@domain:3`. Если такая задача уже стоит в очереди и ещё не отдана агенту, новая не создаётся.
3. Тело команды собирается в момент выдачи агенту из текущего состояния записи, а не в момент изменения. Десять правок подряд, пока сервер был offline, превращаются в одну команду с последним состоянием.
4. Команда описывает желаемое состояние («у пользователя с этим GUID должны быть такие поля»), а не разницу. Агент приводит объект к нему, повтор безопасен.
5. Порядок по зависимостям: подразделение раньше пользователя, пользователь и группа раньше членства. Задача членства ждёт, пока обе стороны не будут созданы.
6. После успеха в привязке запоминается `synced_version` (значение `x_timestamp` или хеш спроецированных полей) и время.
7. Если в домене объект поменяли мимо XOS, это всплывает при периодическом чтении (фаза 4) как расхождение в карточке привязки. Перезаписывает его следующая синхронизация, молча центр ничего не затирает.

Удаление записи в XOS или снятие привязки (решение владельца): объект в AD отключается и переносится в OU отключённых, но не удаляется. Это значение по умолчанию для каждого домена (`delete_policy = disable`). Полное удаление (`delete`) можно включить на домене явно, и тогда оно отдельно подтверждается в окне.

**Пароли (решение владельца).** В `main_user` лежит только хеш Symfony, из него нельзя получить пароль для AD. Поэтому пароль AD задаётся, когда открытый текст есть в запросе: первичный пароль при привязке записи к домену и смена пароля в XOS, если пользователь привязан к доменам. В обоих случаях пароль сразу шифруется ключом агента (раздел 2.9) и уходит отдельной командой `user.set_password` на каждый привязанный домен. Смена пароля в Windows обратно в XOS не приходит, и пароли XOS и домена после этого расходятся. Окно смены пароля в XOS предупреждает, что новый пароль уйдёт и в домены.

**Риск: администратор Main меняет домен.** Пользователь с `ROLE_MAIN`, у которого нет доступа к серверу, правкой карточки в Main фактически меняет объект в AD. Это следствие решения «запись — источник правды», и это нормально. Рекомендация: в карточке пользователя Main показывать список привязанных доменов, а в журнале команды записывать источник: «изменение `main_user` #42 пользователем X».

**Риск: ограничения AD.** `sAMAccountName` не длиннее 20 символов и без ряда спецсимволов, `login` в XOS — до 191. Проверка выполняется при привязке и при сохранении привязанной записи. Конфликт имени с существующим объектом домена даёт ошибку привязки, а не захват чужого объекта.

### 2.6 Модель данных центра

Все таблицы с префиксом `samba_`, модуль `server/src/Samba/`.

| Таблица | Ключевые поля | Примечание |
|---------|---------------|------------|
| `samba_server` | `owner_id` (→ `main_user`, `RESTRICT`), `created_by`, имя, описание, `role` (`ad_dc`, зарезервировано `nt4`), `capabilities` (`dc`, `file`), `domain_id` (nullable до provision), `status` (`new`, `enrolled`, `online`, `stale`, `offline`, `disabled`), `detected` (JSON: `server role`, версии, службы), `expected_timezone`, `time_skew_ms`, `last_seen_at`, `generation`, `applied_generation`, `agent_version`, `protocol_version`, `device_id` (nullable) | Запись инфраструктуры, но владелец — пользователь |
| `samba_server_access` | `server_id`, `user_id` (`CASCADE`), `rights` (битовая маска), `granted_by`, `granted_at` | Уникальная пара `server_id` + `user_id` |
| `samba_enrollment` | `server_id`, `token_hash`, `expires_at`, `used_at`, `created_by` | Одноразовый секрет регистрации |
| `samba_agent_credential` | `server_id`, `kind` (`secret`, `cert`), `secret_hash`, `cert_serial`, `seal_public_key`, `created_at`, `revoked_at` | Действует одна запись; повторная регистрация отзывает прежние |
| `samba_domain` | `owner_id`, `dns_name`, `realm`, `netbios`, `base_dn`, `domain_sid`, `xos_base_ou`, `delete_policy` (по умолчанию `disable`), `write_server_id` | Создаётся по результату provision |
| `samba_directory_link` | `domain_id`, `entity_type` (`user`, `group`, `ou`), `entity_id`, `object_guid`, `sam_account_name`, `dn`, `status` (`pending`, `synced`, `error`, `unlinking`), `synced_version`, `last_error`, `linked_by`, `linked_at` | Уникальная тройка `domain_id` + `entity_type` + `entity_id` |
| `samba_share` | `server_id`, имя, путь, комментарий, `read_only`, `browseable`, `valid_groups` (ссылки на привязанные группы), `options` (JSON из белого списка) | Желаемое состояние шар |
| `samba_command` | `server_id`, `domain_id`, `type`, `capability`, `payload` (JSON без секретов), `sealed` (зашифрованные поля), `precondition` (JSON), `idempotency_key`, `coalesce_key`, `status`, `source` (`manual`, `sync`, `system`), `created_by` (`SET NULL`) и `created_by_login` (копия строкой), `created_at`, `delivered_at`, `finished_at`, `attempt`, `result` (укороченный) | Очередь и журнал одновременно |
| `samba_event` | `server_id`, вид (смена статуса, расхождение роли, перекос времени, смена часового пояса), данные, время | Видно в карточке тем, у кого есть `view` |

`samba_directory_link.entity_id` ссылается на разные таблицы, поэтому внешнего ключа на нём нет. Удаление записи `main_*` ловит тот же слушатель Doctrine (`preRemove`): привязки переходят в `unlinking`, в очередь ставится отключение или удаление объекта AD. Альтернатива — три таблицы привязок с настоящими внешними ключами. Она надёжнее на уровне БД, но втрое увеличивает код синхронизации. Для плана выбрана одна таблица, решение можно пересмотреть на фазе 4.

Сливать сервер Samba с `Device` не нужно, хватит необязательной ссылки `device_id`. Пользователи домена не создаются отдельной копией: объект AD — проекция записи `main_user` через привязку.

### 2.7 Направление и протокол

Соединение открывает агент. Адрес центра один для всех площадок: `https://xos.h1n.ru`.

| Путь | Назначение |
|------|------------|
| `GET /agent/install.sh` | Скрипт установки |
| `GET /agent/xos-agent-<версия>.tar.gz` | Архив агента с уже собранным `vendor/` и контрольной суммой |
| `POST /api/samba/agent/enroll` | Регистрация по одноразовому секрету |
| `GET /api/samba/agent/poll` | Длинный опрос: ждёт команду до 25–30 секунд |
| `POST /api/samba/agent/heartbeat` | Heartbeat |
| `POST /api/samba/agent/result` | Результат команды |
| `wss://xos.h1n.ru/samba/agent` | WebSocket: тот же конверт сообщений одним каналом |

Конверт JSON один для HTTPS и WebSocket: версия протокола, id сообщения, id сервера, вид (`hello`, `heartbeat`, `command`, `result`, `event`), требуемая возможность, ключ идемпотентности, поколение. Схема лежит в `server/agent/protocol/messages.schema.json`. Классы сообщений — общий PHP-код (раздел 2.11), его используют и центр, и агент.

**Риск: WebSocket на стороне центра.** `app` — это `php:8.4-apache`, процесс на запрос. Держать сотни постоянных WebSocket-соединений он не умеет. Рекомендация:

- Фаза 2 работает на длинном опросе HTTPS. Это обычные запросы к Symfony через Apache, новый процесс не нужен. Агент получает команду с задержкой не больше секунды после постановки, если запрос опроса висит.
- Каждый висящий опрос занимает один процесс Apache на всё время ожидания. Десяток агентов — десяток занятых процессов, это терпимо, но `MaxRequestWorkers` нужно поднять с учётом числа серверов, а ожидание держать в 25 секунд при `Timeout` Apache не меньше 60. Внутри ожидания запрос не держит открытую транзакцию и сессию Doctrine, а проверяет очередь коротким запросом раз в секунду.
- WebSocket добавляется отдельным долгоживущим PHP-процессом `samba-hub` в compose (на amphp, рядом с `ssh-gateway`), когда серверов станет много или нужна мгновенная доставка. Apache проксирует к нему путь `/samba/agent` через `mod_proxy_wstunnel` (или `ProxyPass … upgrade=websocket` в Apache 2.4.47+). TLS по-прежнему завершается на Apache, хаб слушает только внутреннюю сеть compose. Хаб только держит соединения и будит агентов, очередь и проверки остаются в Symfony и MySQL.
- Агент умеет оба транспорта с первого дня и сам падает на длинный опрос, если WebSocket недоступен.

Публикация (решение владельца): XOS пока работает на Apache, поэтому TLS для `xos.h1n.ru` завершает сам Apache в контейнере `app`, отдельного прокси перед ним нет. Сейчас compose отдаёт `app` на 8080 без TLS, значит, на фазе 2 нужно:

- включить `mod_ssl` и `mod_headers` в образе, добавить vhost `*:443` для `xos.h1n.ru`;
- смонтировать сертификат и ключ (например, Let's Encrypt, выпущенный на хосте; обновление сертификата — `apachectl graceful` после продления);
- опубликовать в compose порт 443 и оставить 80 только для редиректа и проверки ACME;
- пути `/api/samba/agent/*` и `/agent/*` обслуживает тот же Symfony, `/samba/agent` (WebSocket) Apache проксирует на `samba-hub`, когда он появится.

Если позже перед Apache встанет отдельный прокси (nginx, Traefik), схема не меняется: агенту важен только адрес `https://xos.h1n.ru`. Для mTLS на фазе 6 в этом случае прокси должен пропускать TLS агента насквозь или завершать mTLS сам.

Mercure остаётся каналом браузера. Статус серверов в окна можно публиковать туда после того, как центр принял heartbeat. Команды через Mercure не ходят.

### 2.8 Регистрация и подлинность агента

Учётные данные агента не равны JWT человека и не равны `SSH_GATEWAY_SECRET`.

1. Пользователь с `ROLE_SAMBA` создаёт сервер в приложении и получает одноразовый секрет регистрации и готовую команду установки. В БД лежит только хеш (штатный password hasher Symfony). Срок — 30 минут, использование однократное, повторный показ невозможен.
2. На сервере запускается `install.sh` с секретом. Скрипт кладёт секрет в файл настроек, агент при первом старте вызывает `POST /api/samba/agent/enroll`: секрет, имя хоста, обнаруженное состояние, открытый ключ для запечатывания секретов (раздел 2.9).
3. Центр помечает секрет использованным, привязывает агента к `server_id` и отдаёт постоянный секрет агента. В БД — только хеш. Агент сохраняет секрет в `/var/lib/xos-agent/credentials` (права `0600`) и удаляет секрет регистрации из файла настроек.
4. Дальше агент ходит с заголовком `Authorization: Bearer …` на отдельный файрвол `samba_agent` (шаблон — `server/config/packages/security.php`). Режим `security: false`, как у `ssh_gateway`, сюда не переносится.
5. Действия человека остаются на файрволе `api` с JWT пользователя.

Секрет агента поворачивается из карточки сервера (право `manage`): центр выдаёт новый при следующем запросе агента, старый действует ещё 5 минут и гаснет. Отключение сервера отзывает секрет сразу.

Фаза 6 добавляет mTLS: центр — непубличный CA, подписывает клиентский сертификат на `server_id` по CSR агента, отзыв по серийному номеру. Секрет остаётся вторым фактором.

mTLS делается средствами Apache:

- Отдельный vhost для агентов с `SSLVerifyClient require`, `SSLCACertificateFile` с CA центра и `SSLOptions +StdEnvVars +ExportCertData`. Варианты адреса: тот же `xos.h1n.ru` на отдельном порту (например 8443) или отдельное имя вроде `agent.xos.h1n.ru`. Отдельное имя удобнее, но не обязательно.
- Проверку только на `<Location /api/samba/agent>` внутри общего vhost лучше не делать: при TLS 1.3 смена требований к сертификату внутри соединения (post-handshake auth) у большинства клиентов не работает. Если без отдельного vhost никак, допустим `SSLVerifyClient optional` на весь vhost и проверка `SSL_CLIENT_VERIFY = SUCCESS` в файрволе `samba_agent`.
- Symfony работает в том же процессе Apache (`mod_php`), поэтому данные сертификата берутся из `$_SERVER` (`SSL_CLIENT_VERIFY`, `SSL_CLIENT_M_SERIAL`, `SSL_CLIENT_S_DN_CN`), а не из заголовка, который мог бы подделать клиент.
- Отзыв: файрвол сверяет серийный номер с `samba_agent_credential` при каждом запросе, это мгновенно. CRL в Apache (`SSLCARevocationFile`) — дополнительная мера, её нужно перечитывать через `graceful`.

Истёкший или повторно использованный секрет регистрации и чужой `server_id` получают отказ без тела конфигурации.

### 2.9 Команды и очередь

Источник правды — желаемое состояние в MySQL. Команда — переход к нему, а не произвольный сценарий.

Состояния: `queued`, `delivered`, `running`, `succeeded`, `failed`, `rejected`, `cancelled`. Состояния `expired` больше нет: по решению владельца команды для недоступного сервера копятся до восстановления связи. Отменить команду в очереди может владелец или автор команды, пока она не отдана агенту.

Белый список (имена операций, без произвольной строки shell):

| Возможность | Операции |
|-------------|----------|
| всегда | `state.read` (роль, службы, версии, время), `service.restart` |
| `provision` | `domain.provision` (только на сервере без домена) |
| `dc` | `domain.info`, `directory.read`, `user.ensure`, `user.set_password`, `user.disable`, `user.delete`, `group.ensure`, `group.members`, `ou.ensure`, `dns.read` |
| `file` | `shares.read`, `shares.apply`, `share.remove`, `testparm`, `smbstatus.brief` |

Агент запускает программы списком аргументов, без оболочки. Вывод обрезается до 200 КБ. Ненулевой код или провал `testparm` переводят команду в `failed`, поколение не растёт, предыдущий `smb.conf` остаётся. Перед любой записью в `smb.conf` агент сохраняет копию.

**Очередь при offline.** Все команды копятся, в том числе provision. Чтобы старая команда не сделала вред через неделю:

- У каждой команды есть предусловие: ожидаемое поколение, ожидаемая роль, для provision — «Samba не сконфигурирован, домена нет». Агент проверяет его перед запуском. Не совпало — `rejected` с причиной, ничего не исполняется.
- Команды синхронизации каталога и шар сливаются по ключу и собираются в момент выдачи (раздел 2.5), поэтому после долгого offline приходит последнее состояние, а не вся история.
- Карточка показывает число команд в очереди и возраст самой старой. Provision в очереди выделен отдельно, его можно отменить.
- При восстановлении связи агент сначала шлёт `hello` и полное состояние, центр пересчитывает предусловия и только потом отдаёт очередь по одной команде.

**Секреты в командах.** Пароль администратора домена для provision и пароли пользователей при `user.set_password` нельзя класть в очередь открытым текстом: при offline они лежали бы в MySQL сколько угодно. Рекомендация: при регистрации агент создаёт пару ключей X25519 (`ext-sodium`, есть в стандартной сборке PHP), закрытый ключ остаётся на сервере. Центр шифрует секретные поля открытым ключом агента (`sodium_crypto_box_seal`) прямо в запросе пользователя и пишет в `samba_command.sealed`. Расшифровать может только агент. В журнале видно, что пароль менялся, но не сам пароль. После исполнения `sealed` очищается.

Кто поставил команду, записывается в `samba_command` (пользователь и копия логина, источник). Журнал команд — это и есть эта таблица, его отдаёт API только владельцу сервера.

**Срок хранения журнала (решение владельца): 7 дней, настраивается.**

- Параметр `samba.command_log_retention_days` (переменная окружения `SAMBA_COMMAND_LOG_RETENTION_DAYS`, по умолчанию 7) в `server/src/Samba/config/services.yaml`.
- Чистит консольная команда `php bin/console samba:command:purge`, её запускает cron в контейнере или Symfony Scheduler раз в сутки.
- Удаляются только завершённые команды (`succeeded`, `failed`, `rejected`, `cancelled`), у которых `finished_at` старше срока. Команды в очереди и в работе не удаляются никогда, сколько бы сервер ни был offline: иначе чистка противоречила бы решению «команды копятся до восстановления связи».
- Тот же срок применяется к `samba_event`.
- События уровня сервера в `main.audit` (создан, передан, выдан доступ) этой чисткой не трогаются, у них свой порядок хранения.

### 2.10 Provision нового DC через агент

Существующие серверы с доменом пока не подключаются. Первый DC создаётся из XOS.

1. Владелец создаёт сервер, запускает `install.sh` на чистом Debian или Ubuntu с установленными пакетами Samba (скрипт может поставить их сам по флагу `--install-samba`).
2. Агент регистрируется и сообщает: Samba установлен, provision не выполнен, `smb.conf` по умолчанию, часы и часовой пояс.
3. Владелец заполняет форму: DNS-имя домена, NetBIOS-имя, realm (по умолчанию из DNS-имени), DNS-бэкенд (`SAMBA_INTERNAL` по умолчанию), пароль администратора домена, ожидаемый часовой пояс. Центр проверяет форму и часы (перекос больше 5 минут блокирует кнопку).
4. В очередь ставится `domain.provision` с запечатанным паролем и предусловием «домена нет».
5. Агент проверяет предусловие, сохраняет копию `/etc/samba` и `/etc/krb5.conf`, останавливает `smbd`, `nmbd`, `winbind`, выполняет `samba-tool domain provision --server-role=dc --use-rfc2307 …`, кладёт сгенерированный `krb5.conf`, включает и запускает `samba-ad-dc`, проверяет `samba-tool domain info`.
6. По результату центр создаёт `samba_domain` и привязывает сервер.

**Риск: пароль в аргументах.** `samba-tool domain provision --adminpass` и `user setpassword --newpassword` принимают пароль аргументом, он виден в `/proc/<pid>/cmdline` на время работы команды. Рекомендация: provision запускать без `--adminpass` (Samba сгенерирует случайный пароль), а нужный пароль ставить следующим шагом через локальный `ldbmodify` или LDAP по сокету `ldapi`, передавая его через stdin. Выбрать способ по итогам прототипа фазы 3. Запасной вариант — монтировать `/proc` с `hidepid=2` на сервере.

Подключение уже работающего домена (только чтение, затем запись) — отдельная фаза после этого плана.

### 2.11 Агент

**Язык и состав.** PHP CLI, отдельный долгоживущий процесс под systemd. Symfony на хосте не нужен. Код агента рассчитан на PHP 8.1 и новее (Ubuntu 22.04 — 8.1, Debian 12 — 8.2, Ubuntu 24.04 — 8.3). Центр работает на 8.4, поэтому CI проверяет агент отдельно на 8.1, чтобы в него не попал синтаксис 8.4.

| Задача | Вариант |
|--------|---------|
| Цикл событий, таймеры heartbeat | `amphp/amp` 3 (файберы, PHP 8.1+) |
| WebSocket-клиент | `amphp/websocket-client` |
| HTTPS | `amphp/http-client` |
| Запуск `samba-tool`, `testparm` без блокировки цикла | `amphp/process` |
| Конфиг | `parse_ini_file`, без зависимостей |
| Секреты | `ext-sodium` |

**Риск: долгоживущий PHP-процесс.** PHP редко держат сутками, возможны утечки памяти и зависшие соединения. Рекомендация: amphp вместо синхронного клиента; агент сам перезапускается, когда память превышает порог или прошло N часов; systemd с `Restart=always` и `WatchdogSec`, агент сообщает systemd о живости. Если amphp окажется лишним, запасной вариант — синхронный длинный опрос на `curl` без WebSocket: он проще и тоже укладывается в решения.

**Установка (`install.sh`).** Отдельного пакета нет. Скрипт:

1. Проверяет ОС, версию PHP и расширения (`cli`, `curl`, `sodium`, `openssl`, `json`, `pcntl`), при флаге ставит недостающее через `apt`.
2. Скачивает архив агента с `https://xos.h1n.ru/agent/` и сверяет контрольную сумму, которую показывает карточка сервера.
3. Раскладывает файлы: код в `/opt/xos-agent`, настройки в `/etc/xos-agent/agent.ini` (`0640`), состояние в `/var/lib/xos-agent` (`0700`), unit `/etc/systemd/system/xos-agent.service`.
4. Записывает адрес XOS, `server_id` и секрет регистрации в `agent.ini`, запускает службу.
5. Повторный запуск обновляет агент и не трогает настройки и учётные данные.

Рекомендуется скачать и проверить скрипт, а не запускать `curl … | bash`. Карточка показывает обе команды и контрольную сумму.

**Файл настроек `/etc/xos-agent/agent.ini`.**

```ini
[xos]
url = https://xos.h1n.ru
server_id = 17
enroll_token =            ; удаляется после регистрации
ca_file =                 ; свой CA, если сертификат не публичный

[transport]
prefer = websocket        ; websocket | poll
heartbeat_sec = 30

[samba]
smb_conf = /etc/samba/smb.conf
samba_tool = /usr/bin/samba-tool
share_roots = /srv/samba  ; шары можно создавать только внутри этих каталогов
allow_provision = true    ; false запрещает provision с этого сервера

[agent]
state_dir = /var/lib/xos-agent
log_level = info
```

Локальные ограничения из файла сильнее команд центра: если `share_roots` не включает путь шары, агент отказывает, что бы ни прислал XOS. Это страховка на случай взлома центра. Постоянный секрет и ключи лежат не в `agent.ini`, а в `state_dir`, чтобы файл настроек можно было копировать и показывать.

**Права.** Provision, `samba-tool` на `sam.ldb`, запись `smb.conf` и управление службами требуют root, поэтому агент работает от root. Ограничение — белый список операций, локальные ограничения из файла и защита systemd (`ProtectHome`, `PrivateTmp`, `ReadWritePaths` на `/etc/samba`, `/var/lib/samba`, каталоги шар и `state_dir`).

### 2.12 Время и часовой пояс

Kerberos не принимает перекос часов больше 5 минут, поэтому для DC время — условие работы домена.

Агент в каждом heartbeat присылает: время UTC в миллисекундах, часовой пояс хоста (`timedatectl`: `Timezone`, `NTP synchronized`, `NTP service`), часы RTC в локальном времени или в UTC. Центр сравнивает время агента со своим UTC с поправкой на половину времени запроса.

| Проверка | Предупреждение | Ошибка |
|----------|----------------|--------|
| Перекос часов | больше 30 секунд | больше 4 минут: блокируются provision и команды каталога |
| NTP | синхронизации нет | — |
| Часовой пояс | не совпадает с ожидаемым поясом сервера | — |
| Похоже на путаницу поясов | перекос почти равен целому числу часов, совпадающему со смещением пояса | показывается диагноз: «часы выставлены по местному времени при поясе UTC» или наоборот |

Ожидаемый пояс задаётся в карточке сервера (по умолчанию — пояс установки XOS, например `Europe/Moscow`). Kerberos считает в UTC, поэтому неверный пояс при верном UTC домен не ломает, но путает журналы и расписания. Это предупреждение, а не блокировка.

Все времена в окнах приложения показываются в поясе пользователя XOS с подписью пояса, в БД хранятся в UTC.

DNS домена на этих фазах только читается (`dns.read`) и показывается в карточке. Правка записей DNS — за пределами плана.

### 2.13 Состояние и здоровье

Heartbeat — раз в 30 секунд: версия агента и протокола, hostname, версии пакетов Samba, обнаруженный `server role`, состояние юнитов (`samba-ad-dc`, `smbd`, `nmbd`, `winbind` — какие есть), время и пояс, свободное место на томах Samba и шар, последнее применённое поколение, длина локальной очереди.

Три пропущенных интервала — `stale`, десять — `offline`. Команды при этом продолжают ставиться в очередь. Центр сам на 445 и 22 не опрашивает. `GET /api/health` по-прежнему значит «жив процесс PHP», а не «жив DC».

### 2.14 Версии

`hello` называет версию протокола. Центр принимает текущую и предыдущую. Команда новее, чем понимает агент, получает `rejected` с причиной «обновите агент» и может быть поставлена снова после обновления. Архив агента собирается из того же репозитория, но версия агента своя: серверы обновляются не одновременно с контейнером `app`. Карточка показывает, что доступна новая версия, и команду обновления (повторный `install.sh`).

### 2.15 Безопасность

- Компрометация центра равна компрометации всех подключённых доменов. Защиты: одноразовый секрет регистрации, канал агента отдельно от сессии человека, секреты агента в БД только хешем, белый список операций, локальные ограничения в `agent.ini`, которые центр не может переопределить.
- Пароли домена и пользователей в центре не хранятся ни открыто, ни обратимо: только запечатанные ключом агента до исполнения команды.
- `redeem` SSH отдаёт пароль и ключ по общему заголовку. Для Samba такой обмен не повторяется.
- У агента нет операции «выполни строку».
- Запрет частных адресов в SSH и Ops не снимается: соединение исходящее со стороны агента.
- IP агента не удостоверение. `SYMFONY_TRUSTED_PROXIES` влияет на видимый адрес, проверку секрета — нет.
- Журнал команд — только владельцу, хранится 7 дней (настраивается). В `main.audit` только события уровня сервера.
- TLS завершается на Apache. Ключ сертификата `xos.h1n.ru` и ключ CA агентов (фаза 6) — разные файлы; ключ CA не монтируется в vhost и доступен только команде выпуска сертификатов.
- Удаление владельца не удаляет сервер (`RESTRICT`), передача владения пишется в аудит.
- Изменения записей `main_*` уходят в AD. Права `ROLE_MAIN` на запись теперь влияют на домен, это видно в карточке пользователя.
- Время: перекос больше 4 минут блокирует опасные команды.
- На канал агента — свой лимит частоты, не общий `public_api`.
- `install.sh` и архив проверяются контрольной суммой из карточки.

Исторические файлы окружения в git (их фиксирует `docs/PLAN.md`) для контура, который держит домен, опаснее, чем для стола. Их ротация — отдельное решение владельца, до подключения боевого DC её стоит сделать.

| Код | Куда |

| Стол, Main, Device, Explorer, прикладные модули, SSH, Ops, `ssh-gateway`, Mercure | Остаются как есть |
| `server/src/Samba/` — сущности, API человека, API агента, очередь, слушатель изменений `main_*`, проверка времени | Новый модуль центра |
| `server/src/Samba/setting.json`, строки в `ProtectedAppModules` и `protectedApps.ts` | Тот же модуль: claimant, `ROLE_SAMBA`, «Пуск» |
| Файрвол `samba_agent` в `security.php` | Центр |
| `client/src/apps/samba-*` с `startMenuGroup: 'admin'` | Окна в «Администрировании» |
| `client/src/features/samba` | Запросы и правила |
| Блок «Домены» в карточке пользователя, группы и подразделения Main | Встраивается из `features/samba`, модуль Main о Samba не знает |
| `server/agent/` | Агент, `install.sh`, unit systemd, схема |
| Общие классы сообщений протокола | `server/agent/protocol/`, подключаются в `server/composer.json` через `path`-репозиторий |
| `samba-hub` (WebSocket) | Позже, отдельный сервис в compose |

```
server/src/Samba/

client/src/features/samba/

```

Окна приложения:

| Окно | Фаза |
|------|------|
| `samba-servers` — список серверов, карточка, доступы, установка агента | 1–2 |
| Журнал команд в карточке (только владельцу) | 3 |
| Provision домена | 3 |
| `samba-domains` — домены, привязки, расхождения | 4 |

В CI агент не поднимает Samba: контракт проверяется схемой, PHPUnit очереди и тестом исполнителя с подставными командами. Агент проверяется отдельным заданием на PHP 8.1.

### 2.17 Фазы

Каждая фаза выкладывается отдельно, предыдущие продолжают работать.

**Фаза 0.** Этот документ.

**Фаза 1. Приложение и доступ.** Модуль `Samba`, `ROLE_SAMBA`, `setting.json`, строки в обоих списках защищённых модулей. Окно `samba-servers` в «Администрировании». Таблицы `samba_server`, `samba_server_access`, `samba_enrollment`. Владелец, выдача доступа, передача владения, запрет удаления пользователя с серверами. Агента ещё нет. Готово, когда владелец создаёт сервер и выдаёт `view` другому пользователю, тот видит карточку, но не видит журнал, а удаление владельца отклоняется.

**Фаза 2. Агент и связь.** `server/agent/` на PHP, `install.sh`, `agent.ini`, регистрация, хеш секрета, длинный опрос HTTPS и WebSocket-клиент с откатом на опрос, heartbeat, проверка времени и пояса, TLS на Apache в контейнере `app` (`mod_ssl`, порт 443, сертификат `xos.h1n.ru`), настройка `MaxRequestWorkers` и `Timeout` под длинный опрос. Пара ключей для запечатывания создаётся при регистрации. Очередь ещё пустая. Готово, когда сервер с частным адресом виден online без входящего порта, а сдвинутые часы или неверный пояс дают предупреждение в карточке.

**Фаза 3. Очередь и provision.** `samba_command`, состояния, предусловия, накопление при offline, журнал только владельцу, чистка журнала старше 7 дней (`samba:command:purge`), запечатанные секреты, `state.read`, `service.restart`, `domain.provision`, создание `samba_domain`. Готово, когда provision, поставленный при выключенном агенте, исполняется после включения; повторно поставленный provision на уже созданном домене получает `rejected`; пароля администратора нет ни в БД, ни в журнале; завершённая команда старше срока удаляется, а команда в очереди старше срока остаётся.

**Фаза 4. Каталог `main_*` → домены.** `samba_directory_link`, слушатель изменений, слияние задач, пароль AD при привязке и при смене пароля в XOS, отключение объекта AD при удалении записи, операции `user.*`, `group.*`, `ou.ensure`, `directory.read` для расхождений, блок «Домены» в карточках Main, окно `samba-domains`. Готово, когда один пользователь, привязанный к двум доменам на разных серверах, после смены фамилии в Main получает её в обоих доменах, в том числе на сервере, который был offline во время правки; удаление пользователя в XOS отключает его учётную запись в обоих доменах, но не удаляет её.

**Фаза 5. Шары.** `samba_share`, `shares.apply`, `testparm`, ACL, `share_roots` из `agent.ini`, доступ по привязанным группам. Готово, когда правка шары на DC не меняет `server role`, не трогает `[global]` и `sam.ldb`, а путь вне `share_roots` отклоняется агентом.

Фазы 4 и 5 друг от друга не зависят, их можно поменять местами.

**Фаза 6. mTLS.** CA центра, CSR при регистрации, отзыв по серийному номеру, поворот сертификата из карточки, отдельный vhost Apache с `SSLVerifyClient require` (отдельный порт или, по желанию, имя вроде `agent.xos.h1n.ru`). Готово, когда отозванный сертификат и секрет прошлой регистрации получают отказ.

**После плана:** хаб `samba-hub` для WebSocket, подключение существующих серверов с доменом (сначала чтение), второй DC в домене, классический домен NT4, рядовой член домена как файловый сервер, правка DNS, вложенные группы, обратная синхронизация паролей, обзор шар в проводнике.

### 3.1 Напряжения и как их снять

| Решение | Что мешает | Рекомендация |
|---------|-----------|--------------|
| Серверы закреплены за пользователем | Каскадное удаление снесло бы DC из реестра | `owner_id` с `RESTRICT`, передача владения, блокировка вместо удаления (2.4) |
| Журнал только владельцу | `main.audit` читают администраторы Main | В `main.audit` только события уровня сервера, детали — в `samba_command` (2.4) |
| Команды копятся, включая provision | Старая команда может сработать на изменившемся сервере | Предусловия, проверка агентом перед запуском, отмена, выделение в карточке (2.9) |
| Копятся и команды с паролями | Пароль лежал бы в MySQL всё время offline | Запечатывание ключом агента, очистка после исполнения (2.9) |
| Запись `main_*` — источник для AD | В `main_user` только хеш пароля; администратор Main меняет домен | Пароль задаётся при привязке и смене пароля; домены видны в карточке Main (2.5) |
| Агент на PHP | Долгоживущий процесс и WebSocket — не родная среда PHP | amphp, самоперезапуск, watchdog; запасной вариант — длинный опрос (2.11) |
| WebSocket к центру | `php:8.4-apache` не держит постоянные соединения | Фаза 2 на длинном опросе, позже процесс `samba-hub` за `mod_proxy_wstunnel` (2.7) |
| Длинный опрос на Apache | Каждый агент держит процесс Apache до 25 секунд | Поднять `MaxRequestWorkers`, `Timeout` ≥ 60, без транзакции во время ожидания; при росте числа серверов — `samba-hub` (2.7) |
| mTLS на Apache | Проверка сертификата только на пути внутри общего vhost ломается на TLS 1.3 | Отдельный vhost (порт или имя) с `SSLVerifyClient require` (2.8) |
| Журнал 7 дней при накоплении команд | Чистка могла бы удалить ещё не исполненные команды | Чистятся только завершённые команды по `finished_at` (2.9) |
| Пароли не возвращаются из Windows | Пароли XOS и домена расходятся | Предупреждение в окне смены пароля; обратная синхронизация — после плана (2.5) |
| Пароль в аргументах `samba-tool` | Виден в `/proc` | Пароль через stdin в `ldbmodify` / `ldapi`, запасной вариант `hidepid=2` (2.10) |
| Агент от root | Ошибка белого списка опаснее | Белый список, локальные ограничения `agent.ini`, защита systemd (2.11) |

Открытых вопросов по плану не осталось.

### 3.2 Риски, которые фазы не снимают сами

- Агент по сути администратор домена. Ошибка белого списка опаснее ошибки в окне задач.
- Синхронизация из `main_*` делает ошибку в Main ошибкой в домене: случайная блокировка пользователя в XOS отключит его во всех привязанных доменах.
- Длинная очередь после долгого offline может принести много изменений сразу. Слияние по ключу уменьшает объём, но владелец должен видеть очередь до восстановления связи.
- 7 дней журнала — короткий срок для разбора инцидента в домене. Если что-то нужно хранить дольше, срок поднимается параметром без изменения кода.
- Исторические секреты в git становятся границей доверия всей схемы, как только к XOS подключат боевой DC.
